## Продукт

Два процесса в одном Compose:

- `kitchen-api` — площадка (каталог, корзина, заказы, partner API), порт 8080.
- `partner-demo` — одно демо-заведение, порт 8081. Меню и `stock_qty` **в памяти процесса**, без своей БД. При старте само делает `PUT /partner/menu` на площадку.

Postgres — остатки, брони, корзины, заказы, меню. Redis — только копия витрины (имя, цена, открыто ли, `is_active`). Если Redis молчит, каталог читается из Postgres, пользователю не 500. Свободный остаток `available_qty` = `stock_qty` минус живые брони; в Redis его нет, считается на каждый `GET .../menu`.

### Что главное (по убыванию)

1. Частичный отказ корзины: validate и create честно говорят, что можно оформить, а что нет (`ok` / `partial` / `invalid`).
2. `Idempotency-Key` на `POST /orders`: повтор не создаёт второй заказ.
3. Бронь блюда на **10 минут** в Postgres (`dish_reservations.expires_at`). Гонка за последнюю порцию — `SELECT … FOR UPDATE` по блюду, не check-then-act.
4. Дедлайн заведения **15 минут** (`orders.confirm_until`). Не подтвердили — заказ `cancelled`, остаток возвращается. Без отдельного воркера: проверка в момент GET/списков/смены статуса.
5. История статусов в `order_status_history`, отдаётся в `GET /orders/{id}` как `status_history`.

Validate только подсказывает. Create **ещё раз** проверяет бронь и остатки. После создания HTTP notify заведению не дольше **2 секунд**. Не успело — заказ уже есть, статус `pending_confirmation`, заведение потом само заберёт список (`GET /partner/orders`).

### Правила из сценариев

- Одна корзина = одно заведение. Чужое блюдо → `409`, сначала `DELETE /cart` (брони отпускаются).
- qty строго > 0. Уменьшить / убрать / очистить — бронь отпускается. Увеличить — добрать остаток или `409`, прежнее qty не менять.
- Отмена пользователем только из `created` и `pending_confirmation`. С `confirmed` (дальше cooking → delivering → completed) — `409`.
- `is_active = false` — не то же самое, что `stock_qty = 0`. Живые брони на блюдо снять сразу, кэш витрины сбросить.
- Пустой список заведений и пустое меню — `200`, не ошибка. Неизвестный id — `400`/`404`, не `500`.
- `delivery_address` — строка для статуса «в доставке», без курьера.
- Причины позиций: только `reservation_expired` | `out_of_stock` | `dish_inactive`. Блокеры: только `restaurant_closed` | `below_min_order` | `empty_cart`.

Статусы заказа: `created` → `pending_confirmation` → `confirmed` → `cooking` → `delivering` → `completed`. Отклонения: `cancelled`, `rejected`.

Связь с заведением: `dishes.external_id` + `restaurants.api_key_hash`. Связь с пользователем: `user_id` текстом из заголовка.

## Partner-demo

Отдельный сервис, не второй Postgres. Notify: `POST /internal/orders/notify`. Демо сверяет позиции со своим локальным стоком и шлёт `POST /partner/orders/{id}/status` (confirm или reject). Повтор того же `order_id` сток не списывает. `PATCH /internal/dishes/{externalId}` меняет только память демо — чтобы показать развилку «на площадке ещё есть, у кухни уже нет».

## Чего не делать

- Логин пользователя, OAuth, отдельный сервис auth.
- Фронт, курьер, трекинг, слоты доставки.
- Вторая БД у partner-demo в этом MVP.
- Кладсть бронь или `available_qty` в Redis.
- Путать TTL: бронь 10 мин, confirm 15 мин, notify 2 сек, кэш витрины — разные вещи.
- Расширять enum причин и блокеров свободным текстом.
