# Решения

Сценарии: [CJM пользователя](cjm/user-cjm.puml), [CJM заведения](cjm/restaurant-cjm.puml).  
API: [endpoints.md](api/endpoints.md), [openapi.yaml](../api/openapi.yaml). Swagger UI: `/swagger/index.html`.

## Приоритеты

1. **Частичный отказ корзины** — API говорит, что можно оформить, а что нет.
2. **Idempotency-Key** — повторный «Оформить» не создаёт второй заказ.
3. **Бронь на 10 минут** — позиция занимает остаток в Postgres (`dish_reservations.expires_at`).
4. **Дедлайн заведения** — если не подтвердили до `orders.confirm_until`, заказ отменяется, остаток возвращается.
5. **История статусов** — каждая смена пишется в `order_status_history` и отдаётся в `GET /orders/{id}`.

Проверка корзины только подсказывает. Создание заказа проверяет бронь и остатки ещё раз. Потом площадка ждёт заведение ограниченное время.

## Где что хранится

| Данные | Где | Redis |
|--------|-----|--------|
| Остатки, брони, корзина, заказы | Postgres | нет, гонка за порцию в транзакции |
| Карточка заведения, состав меню | Postgres + копия в Redis | быстрее список и витрина |
| `available_qty` | Postgres: `stock_qty` минус живые брони | не кэшируем |

Если Redis не ответил — каталог из Postgres, не 500.  
Кэш сбрасываем при `PUT /partner/menu`, `PATCH /partner/restaurant`, `PATCH /partner/dishes/{externalId}`. Корзина и заказ Redis не трогают.

## Сроки

| Что | Где | Сколько |
|-----|-----|---------|
| Бронь в корзине | Postgres `expires_at` | 10 минут |
| Ожидание заведения | Postgres `confirm_until` | 15 минут |
| HTTP-уведомление | сеть | 2 секунды |
| Копия меню | Redis | минуты |

Первые два — продукт. Третий — сеть: заказ у нас уже есть, заведение потом само запросит список. Redis бронь и дедлайн не заменяет.

## Правила

- Одна корзина = одно заведение. Смена — после `DELETE /cart`.
- Количество можно убавить, убрать, увеличить (если хватает остатка) или очистить корзину.
- Отмена — из `created` / `pending_confirmation`. С `confirmed` нельзя.
- `is_active = false` — живые брони на блюдо снимаем сразу, кэш витрины сбрасываем.
- Уведомление не дошло — заказ всё равно виден в `GET /partner/orders`.
- `qty` > 0; блюдо из заведения корзины; неизвестный id — `400`/`404`; пустой каталог — `200`.

## Упрощения

- Нет логина, есть `X-User-Id`. Заведение ходит с `X-Api-Key`.
- Остатки и брони у площадки. Заведение присылает меню и stock.
- Просроченные брони и `confirm_until` смотрим в момент запроса, без воркера.
- `delivery_address` — строка для статуса «в доставке».
- Одно демо-заведение. Меню и сток `partner-demo` — в памяти процесса. Confirm/reject считает по своему `stock_qty`. Клиенту площадка отвечает из Postgres.
