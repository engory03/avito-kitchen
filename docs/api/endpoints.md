# API — что умеет сервис

Базовый путь: `/api/v1`

- Пользователь передаёт заголовок `X-User-Id` (строка, не сессия).
- Заведение передаёт `X-Api-Key`.

Сценарии, под которые сделаны запросы: [CJM пользователя](../cjm/user-cjm.puml) и [CJM заведения](../cjm/restaurant-cjm.puml).

## Для клиента (web)

### Заведения и меню

| Метод | Путь | Зачем |
|-------|------|--------|
| GET | `/restaurants` | Список (фильтр: кухня / только открытые). Пустой список — нормальный ответ. |
| GET | `/restaurants/{id}` | Одно заведение |
| GET | `/restaurants/{id}/menu` | Меню; у блюда видно, сколько ещё можно взять. Может быть пустым. |

Список и витрина меню (имя, цена, открыто ли, `is_active`) могут читаться из Redis. Свободный остаток `available_qty` всегда считается из Postgres — он зависит от живых броней. Для клиента URL те же.

### Корзина и бронь

При добавлении блюдо **бронируется на 10 минут**. В корзине блюда только из **одного** заведения.

| Метод | Путь | Зачем |
|-------|------|--------|
| GET | `/cart` | Текущая корзина + до какого времени бронь |
| POST | `/cart/items` | Добавить блюдо (создать/увеличить бронь). `qty` строго > 0 |
| PATCH | `/cart/items/{itemId}` | Изменить количество. `qty` строго > 0 |
| DELETE | `/cart/items/{itemId}` | Убрать позицию (снять бронь) |
| DELETE | `/cart` | Очистить корзину целиком (снять все брони) |

`PATCH /cart/items/{itemId}`:
- **Уменьшение** количества — освобождается часть брони, всегда успешно.
- **Увеличение** количества — система пытается забронировать разницу; если остатка не хватает — `409`, количество остаётся прежним.

Тело `POST /cart/items`:

```json
{ "dish_id": "uuid", "qty": 1 }
```

Ответ:

```json
{
  "cart_item_id": "uuid",
  "dish_id": "uuid",
  "qty": 1,
  "reservation_expires_at": "2026-09-05T20:40:00Z"
}
```

Частые ошибки:

- `400` количество ≤ 0 или невалидный `dish_id`;
- `404` блюда нет;
- `409` нет остатка (в том числе при увеличении количества уже добавленной позиции);
- `409` в корзине уже другое заведение — сначала `DELETE /cart`, потом снова добавить;
- `422` заведение закрыто / блюдо снято с меню.

Пустой список заведений и пустое меню — это `200` с пустым массивом, не ошибка.

### Проверка перед заказом

| Метод | Путь | Зачем |
|-------|------|--------|
| POST | `/cart/validate` | Проверить корзину **без** создания заказа |

Ответ:

```json
{
  "status": "ok | partial | invalid",
  "valid_items": [
    { "dish_id": "uuid", "qty": 1, "reservation_expires_at": "..." }
  ],
  "invalid_items": [
    { "dish_id": "uuid", "qty": 1, "reason": "reservation_expired | out_of_stock | dish_inactive" }
  ],
  "blockers": ["restaurant_closed", "below_min_order", "empty_cart"]
}
```

- `ok` — можно заказывать всё
- `partial` — часть нельзя; можно заказать только хорошие позиции
- `invalid` — заказ нельзя (закрыто, пустая корзина, не набрана минимальная сумма)

### Заказы

| Метод | Путь | Зачем |
|-------|------|--------|
| POST | `/orders` | Создать заказ. Нужен заголовок `Idempotency-Key` |
| GET | `/orders/{id}` | Статус, состав и история статусов. Если дедлайн подтверждения вышел — заказ уже `cancelled` |
| GET | `/users/{userId}/orders` | История заказов |
| POST | `/orders/{id}/cancel` | Отменить из `created` или `pending_confirmation`. С `confirmed` — нельзя |

Тело `POST /orders`:

```json
{
  "accept_partial": true,
  "delivery_address": "ул. Пример, 1"
}
```

`delivery_address` — строка для статуса «в доставке», без курьера и трекинга.

Ответ `GET /orders/{id}` включает историю смен статуса:

```json
{
  "id": "uuid",
  "status": "confirmed",
  "items": [...],
  "confirm_until": "2026-09-05T21:00:00Z",
  "status_history": [
    { "from_status": null, "to_status": "created", "changed_by": "user", "created_at": "..." },
    { "from_status": "created", "to_status": "pending_confirmation", "changed_by": "system", "reason": "partner_timeout_2s", "created_at": "..." },
    { "from_status": "pending_confirmation", "to_status": "confirmed", "changed_by": "restaurant", "created_at": "..." }
  ]
}
```

Что происходит при создании:

1. Если такой `Idempotency-Key` уже был — вернём старый заказ.
2. Ещё раз проверим брони и остатки (как validate).
3. Если часть позиций плохая и `accept_partial` = false — ошибка.
4. Если всё совсем плохо — ошибка.
5. В одной транзакции: заказ в статусе `created`, списание броней и остатка, запись в историю статусов, `confirm_until` = сейчас + 15 минут.
6. Коротко уведомляем заведение (не больше 2 секунд). Если не ответило — статус `pending_confirmation`. Заказ у нас есть, заведение потом само спросит список.

Статусы заказа:

`created` → `pending_confirmation` → `confirmed` → `cooking` → `delivering` → `completed`

Отклонения: `cancelled` (пользователь или вышел дедлайн), `rejected` (заведение отказало).

Отмена (`POST /orders/{id}/cancel`) разрешена из `created` и `pending_confirmation`.
С `confirmed` и дальше (`cooking` → `delivering` → `completed`) — `409`: ресурсы уже выделены, отмена недоступна.

## Для заведения (partner API на kitchen-api)

| Метод | Путь | Зачем |
|-------|------|--------|
| PUT | `/partner/menu` | Загрузить/обновить меню и остатки |
| PATCH | `/partner/restaurant` | Открыто/закрыто |
| PATCH | `/partner/dishes/{externalId}` | Остаток и/или снять блюдо с меню (`is_active`) |
| GET | `/partner/orders` | Забрать заказы (догон, если уведомление не дошло) |
| POST | `/partner/orders/{id}/status` | Подтвердить, отклонить, сменить этап готовки |

Тело смены статуса:

```json
{ "status": "confirmed", "reason": "принято в работу" }
```

Тело обновления блюда:

```json
{ "stock_qty": 0, "is_active": false }
```

Если `is_active = false`, живые брони на это блюдо снимаются сразу.

Статус заказа меняется только по понятным правилам (нельзя из `completed` прыгнуть в `cooking`). Иначе `409`.
Неизвестный заказ или `external_id` — `404`, не `500`.
Если заведение отвечает уже после дедлайна — заказ к этому моменту `cancelled`, смена статуса не пройдёт.

## Демо-сервис заведения (partner-demo)

Отдельный процесс в Compose, не второй Postgres. Меню и `stock_qty` держит **в памяти**. Площадка по-прежнему списывает остаток у себя при создании заказа; демо сверяет **свой** склад и отвечает confirm/reject.

| Метод | Путь | Зачем |
|-------|------|--------|
| GET | `/health` | Жив ли сервис |
| GET | `/internal/menu` | Локальное меню и текущий локальный сток |
| PATCH | `/internal/dishes/{externalId}` | Поменять только локальный остаток (площадку не трогает) |
| POST | `/internal/orders/notify` | Площадка сообщает о новом заказе |

При старте демо само отправляет меню на площадку (`PUT /partner/menu`).

При `POST /internal/orders/notify` заведение сверяет позиции со своим локальным `stock_qty` и сразу шлёт `POST /partner/orders/{id}/status` confirm или reject (без своей БД). Повтор того же `order_id` повторно сток не списывает. Если уведомление не дошло — площадка узнает результат позже через `GET /partner/orders` (pull).

`PATCH /internal/dishes/{externalId}` нужен, чтобы показать развилку CJM «на площадке ещё есть, у кухни уже нет»: локальный сток обнулили, клиент всё ещё может оформить заказ на kitchen-api, демо отклонит.
